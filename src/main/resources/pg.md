# PostgreSQL 16 для метаданных SeaweedFS: финальное описание конфигурации

## Коротко

- **Чем ограничена производительность.** Предел задаёт задержка `fsync` на потребительских SSD, а не 20 ядер и не 140 ГБ
  памяти.
- **Ожидаемая нагрузка:** ~5–15 тыс. записей метаданных в секунду и 50–100+ тыс. чтений в секунду.
- **По объёму:** порядка 1–2 млрд файлов на диске, из них ~150–250 млн полностью в RAM.
- **Главные риски:** диски без защиты от потери питания (PLP), их износ (причём синхронный в зеркалах) и единственный
  сервер.
- **Без чего в прод нельзя:** потоковая реплика, бэкапы с архивом WAL и мониторинг износа SSD.

## 0. Исходные допущения

Если что-то из этого неверно, часть значений нужно пересчитать.

- 140 ГБ памяти и 20 ядер отданы PostgreSQL. Остальная нагрузка на хосте (меньше 5%) живёт в отдельных лимитах.
- RAID10 из 4+ SATA SSD Patriot, полезный объём ~3.5 ТБ. Данные и WAL лежат на одном массиве.
- SeaweedFS filer работает через store `postgres2`. Apicurio — отдельная база с малой нагрузкой.
- Основной профиль — OLTP: точечные операции по первичному ключу и короткие range-scan'ы при листинге директорий.

## 1. Распределение памяти (140 ГБ)

| Потребитель                                     | Объём      |
|-------------------------------------------------|------------|
| `shared_buffers` (в huge pages)                 | 32 ГБ      |
| autovacuum: 6 воркеров × 1 ГБ                   | до 6 ГБ    |
| `maintenance_work_mem` (ручные VACUUM, индексы) | 2–4 ГБ     |
| `work_mem` × активные запросы                   | ~3–5 ГБ    |
| Сами backend-процессы (300 × ~5–10 МБ)          | ~2–3 ГБ    |
| **Page cache ОС**                               | **~90 ГБ** |

PostgreSQL рассчитан на двойное кэширование: свой буферный кэш плюс page cache ОС. Отдавать в `shared_buffers` бо́льшую
часть памяти невыгодно: подробнее в разделе 4.

---

## 2. Диски и RAID

**RAID10, а не RAID5/6.** У RAID5/6 каждая мелкая запись превращается в чтение и запись чётности, то есть 4–6 операций
ввода-вывода вместо 2. Для мелкой случайной записи, из которой и состоит WAL и страницы `filemeta`, это смертельно. К
тому же ребилд RAID5/6 на потребительских SSD долгий и опасный.

**Данные и WAL на одном массиве.** Если вынести WAL на отдельную пару дисков, у данных останется меньше шпинделей, а
пара под WAL будет изнашиваться в разы быстрее. На 4–6 дисках один общий RAID10 эффективнее.

**Режим кэша записи:**

- **Аппаратный контроллер с батареей или флеш-модулем кэша (BBU):** кэш контроллера в режим write-back, кэш самих дисков
  выключить. Тогда `fsync` подтверждает контроллер, задержка ~0.1 мс, а производительность записи вырастет в разы.
- **mdadm или контроллер без BBU:** кэш дисков оставить включённым, иначе потребительский SSD становится очень
  медленным. Обязательно проверить, что команда flush реально сбрасывает данные. Это делается утилитой `diskchecker.pl`
  с отключением питания на тесте.

**Over-provisioning.** Не размечайте последние 10–15% массива или держите заполнение ниже 70–80%. Потребительские SSD
резко замедляются при заполнении, потому что контроллеру не хватает свободных блоков для сборки мусора.

**TRIM** запускайте по расписанию (`fstrim.timer`, раз в неделю). Опция `discard` при монтировании даёт на
потребительских SSD всплески задержек при каждом удалении.

## 3. ОС (Linux)

```ini
# /etc/sysctl.d/90-postgres.conf

vm.swappiness = 1
# Не 0: на современных ядрах 0 означает «не свопить почти никогда», и при нехватке
# памяти раньше сработает OOM killer. Значение 1 оставляет своп как аварийный клапан.

vm.dirty_background_bytes = 268435456     # 256 МБ
vm.dirty_bytes = 1073741824               # 1 ГБ
# По умолчанию лимиты задаются в процентах RAM: 10% и 20%, то есть 14–28 ГБ грязных
# страниц. В момент fsync на чекпоинте всё это уходит на диск разом и вызывает
# многосекундные паузы. Фиксированные небольшие значения сглаживают запись.
# Меньше 256 МБ не нужно: ядро начнёт писать слишком мелкими порциями.

vm.overcommit_memory = 2
vm.overcommit_ratio = 80                  # пересчитать, см. ниже
# Без overcommit OOM killer может убить postmaster или backend; тогда PostgreSQL
# перезапускает все подключения. В режиме 2 malloc просто вернёт ошибку,
# и упадёт только один запрос.
# Важно: huge pages вычитаются из CommitLimit, поэтому ratio подбирайте так,
# чтобы CommitLimit в /proc/meminfo был ≈ RAM − hugepages − 5 ГБ.
# Если на хосте есть JVM или другие процессы, резервирующие много виртуальной
# памяти, режим 2 может их сломать. Тогда оставьте 0, а postmaster защитите
# через OOMScoreAdjust=-1000 в systemd.

vm.nr_hugepages = <значение>
# Узнать: postgres -D $PGDATA -C shared_memory_size_in_huge_pages (на остановленном
# кластере). Для 32 ГБ shared_buffers это ~16500 страниц по 2 МБ.

vm.zone_reclaim_mode = 0
# На NUMA-машинах значение 1 заставляет ядро вытеснять page cache вместо того,
# чтобы брать память с соседнего узла. Для PostgreSQL это плохо.
```

**Почему huge pages обязательны.** Каждый backend отображает в своё адресное пространство все `shared_buffers`. С
обычными страницами по 4 КБ таблица страниц на 32 ГБ занимает до ~64 МБ на один процесс. При 300 подключениях это ~19 ГБ
памяти только на таблицы страниц, плюс промахи TLB. С huge pages по 2 МБ это мегабайты.

**Transparent Huge Pages (THP): `never`.** Задаётся через `transparent_hugepage=never` в параметрах ядра. Фоновая
дефрагментация THP (khugepaged, compaction) даёт непредсказуемые паузы. Явные huge pages выше дают ту же выгоду без этих
пауз.

**Файловая система: XFS с `noatime`.** XFS хорошо ведёт себя при параллельной записи и на больших файловых системах.
ext4 тоже подойдёт. `noatime` убирает запись времени доступа на каждое чтение файла.

**I/O scheduler: `none`.** Для mdadm на SSD это правильно: SSD сами планируют запросы, а планировщик ядра только
добавляет задержку. Для аппаратного RAID подойдёт и `mq-deadline`. CFQ и BFQ не используйте.

**CPU governor: `performance`.** Задержка коммита — это короткие всплески работы CPU. Переходы ядер между уровнями
энергосбережения (C-states/P-states) добавляют к ним десятки микросекунд.

**Изоляция в systemd** (`postgresql.service`):

```ini
[Service]
AllowedCPUs=0-19          # если 2 сокета, по возможности все ядра на одном NUMA-узле
MemoryHigh=150G           # мягкий лимит; учтите, что в него входит page cache
OOMScoreAdjust=-1000
LimitNOFILE=65536
```

Это защищает PostgreSQL от соседних нагрузок, но не мешает ему использовать свои ресурсы.

## 4. postgresql.conf с обоснованием

### Подключения и защита

```ini
listen_addresses = '*'
max_connections = 300
# Оптимум по одновременно активным запросам — 2–4 на ядро, то есть 40–80.
# 300 — это запас под пулы нескольких filer, Apicurio и служебные подключения;
# большинство из них простаивает. Больше 300–500 не ставьте: растёт стоимость
# снимков (snapshot) и конкуренция за блокировки. Если клиентов больше, нужен PgBouncer.

superuser_reserved_connections = 5
# Чтобы админ мог зайти, даже если пулы выбрали все подключения.

idle_in_transaction_session_timeout = 60s
# Брошенная открытая транзакция держит горизонт видимости: autovacuum не может
# удалить мёртвые строки, и filemeta начинает раздуваться. Минута — это намного
# больше любой нормальной транзакции SeaweedFS, которые длятся миллисекунды.

tcp_keepalives_idle = 60
tcp_keepalives_interval = 10
tcp_keepalives_count = 6
# Быстрое обнаружение разорванных соединений (падение filer, сбой сети).
# По умолчанию ОС ждёт 2 часа, и всё это время соединение может держать блокировки.

password_encryption = scram-sha-256
```

`statement_timeout` глобально **не ставим**: Apicurio и ручные админские запросы могут быть долгими. Задаём его на
уровне ролей (раздел 5).

### Память

```ini
shared_buffers = 32GB
# Правило «25% RAM». Больше не нужно, потому что:
#  - остальное всё равно работает как кэш через page cache ОС;
#  - чем больше shared_buffers, тем больше грязных страниц на чекпоинте
#    и тем сильнее всплески записи;
#  - выгода от увеличения выше 25–40% обычно мала.
# Меньше (8–16 ГБ) тоже плохо: горячие страницы индекса filemeta будут
# постоянно ходить между двумя кэшами.

huge_pages = on
# Именно on, а не try: если huge pages не настроены, PostgreSQL не стартует,
# и ошибку конфигурации видно сразу. С try он молча запустится без них и будет
# расходовать ~19 ГБ на таблицы страниц (см. раздел 3).

effective_cache_size = 100GB
# Это не выделение памяти, а подсказка планировщику: сколько данных в сумме
# в shared_buffers и page cache. Влияет на выбор индексного доступа. 32 + ~70 ГБ.

work_mem = 32MB
# Лимит на одну операцию сортировки или хеширования, а не на подключение.
# Запросы SeaweedFS почти не сортируют: используется ORDER BY name по индексу.
# 32 МБ хватает Apicurio и админским запросам. Больше (256 МБ+) опасно:
# 300 подключений × несколько операций — и можно уйти в OOM.

maintenance_work_mem = 2GB
# Для CREATE INDEX, REINDEX и ручного VACUUM. Индекс filemeta на сотни миллионов
# строк строится заметно быстрее. Больше 2 ГБ даёт мало, а одновременных операций
# обслуживания обычно одна-две.

autovacuum_work_mem = 1GB
# В PG16 VACUUM всё равно не использует больше 1 ГБ на список мёртвых строк
# (~180 млн TID), так что это максимум, который реально работает. Меньшее значение
# заставит VACUUM на большой таблице многократно проходить по всем индексам.
# Худший случай — 6 воркеров × 1 ГБ = 6 ГБ, это укладывается в бюджет.
```

### CPU и параллелизм

```ini
max_worker_processes = 20
max_parallel_workers = 10
max_parallel_workers_per_gather = 2
max_parallel_maintenance_workers = 4
# Нагрузка OLTP: параллельные планы почти не нужны, а каждый параллельный воркер
# отнимает ядро у коммитов. Лимит в 10 из 20 ядер гарантирует, что тяжёлый
# аналитический запрос не съест всю машину. 2 воркера на запрос хватает
# для редких отчётов. 4 воркера на обслуживание ускоряют CREATE INDEX и REINDEX.

jit = off
# JIT окупается только на тяжёлых аналитических запросах. На точечных запросах
# SeaweedFS он может добавить десятки миллисекунд компиляции, если планировщик
# ошибётся с оценкой стоимости.
```

### WAL, коммиты и чекпоинты

```ini
wal_level = replica
# Нужен для потоковой реплики и PITR. logical не включаем: больше WAL,
# а логическая репликация здесь не нужна.

synchronous_commit = on
# Коммит подтверждается только после fsync WAL. Для метаданных SeaweedFS потеря
# подтверждённой записи означает «потерянный» файл: данные лежат на volume-серверах,
# а ссылки на них нет. Цена — потолок записи определяется fsync.
# Значение off на уровне роли SeaweedFS — сознательный компромисс на случай,
# если производительности не хватит. Риск: потеря последних ~30 мс подтверждённых
# транзакций при сбое (это 3 × wal_writer_delay); порчи базы при этом не будет.

wal_writer_delay = 10ms
# По умолчанию 200 мс. Влияет только на асинхронные коммиты: уменьшает окно
# потерь с ~600 мс до ~30 мс, если где-то включат synchronous_commit = off.
# На синхронные коммиты не влияет.

commit_delay = 0
commit_siblings = 5
# Group commit в PostgreSQL работает и без этого. commit_delay (микросекунды)
# стоит пробовать только если по метрикам упираемся в fsync: начать с 200–500.
# Он немного увеличивает задержку одиночного коммита, но повышает общую пропускную
# способность. Без замеров не трогаем.

wal_buffers = 64MB
# По умолчанию 1/32 от shared_buffers, но не больше 16 МБ. При сотне параллельных
# пишущих сессий 16 МБ может заполняться между сбросами, и тогда backend ждёт.
# Больше 64 МБ выгоды не даёт.

wal_compression = lz4
# Сжимает полные образы страниц (full-page images). После чекпоинта первое
# изменение каждой страницы пишет её в WAL целиком, все 8 КБ, и именно это
# основной объём WAL. lz4 сжимает в 2–4 раза при минимальной нагрузке на CPU.
# Почему не zstd: он сжимает чуть лучше, но дороже по CPU, а CPU нам нужен
# для коммитов. Для потребительских SSD меньше WAL — это прямая экономия ресурса.

max_wal_size = 24GB
min_wal_size = 4GB
checkpoint_timeout = 15min
checkpoint_completion_target = 0.9
# Чекпоинты должны срабатывать по времени (раз в 15 мин), а не из-за объёма WAL.
# При ~10–20 МБ/с WAL за 15 минут набегает 9–18 ГБ, отсюда 24 ГБ с запасом.
# Почему 15 мин, а не 5 (по умолчанию): каждый чекпоинт «обнуляет» страницы,
#   и следующее изменение снова пишет полную страницу. Реже чекпоинты —
#   кратно меньше WAL и износа SSD.
# Почему не 30–60 мин: дольше восстановление после сбоя (replay всего WAL
#   с последнего чекпоинта). 24 ГБ на этих дисках проигрываются за ~2–5 минут;
#   это приемлемое время простоя.
# completion_target 0.9 растягивает запись чекпоинта на 90% интервала,
#   чтобы не было всплесков.
# min_wal_size 4 ГБ: держит заранее созданные сегменты WAL, чтобы не создавать
#   их на лету во время всплесков.

max_slot_wal_keep_size = 200GB
# Если реплика отстанет или отвалится, её слот репликации держит WAL бесконечно,
# пока диск не заполнится и мастер не упадёт. 200 ГБ (~6% диска) — это часы
# отставания. После превышения слот инвалидируется, реплику придётся пересоздать,
# зато мастер выживет.

full_page_writes = on
fsync = on
# Не трогать никогда, тем более на SSD без PLP.
```

### Архив WAL и репликация

```ini
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'
archive_timeout = 60s
# Архив нужен для PITR: восстановления на момент до ошибки, например до массового
# случайного удаления через SeaweedFS. archive_timeout ограничивает потерю данных
# при гибели всего сервера одной минутой даже при низкой нагрузке.
# Почему не меньше: каждый принудительный сегмент весит 16 МБ, поэтому
# на маленьких интервалах архив раздувается.

max_wal_senders = 10
max_replication_slots = 10
# Запас под реплику, pg_basebackup и будущие нужды; само по себе это ничего не стоит.

wal_keep_size = 0
# Удержание WAL для реплики обеспечивает слот, а не этот параметр.
```

### Планировщик под SSD

```ini
random_page_cost = 1.1
seq_page_cost = 1.0
# Значение по умолчанию 4.0 рассчитано на HDD, где случайное чтение в 4 раза
# дороже последовательного. На SSD они почти равны. При 4.0 планировщик иногда
# выбирает seq scan по filemeta вместо индекса. 1.1 вместо 1.0 оставляет индексу
# лёгкое преимущество, но не делает его бесплатным.

effective_io_concurrency = 200
maintenance_io_concurrency = 200
# Глубина предвыборки для bitmap heap scan, ANALYZE и восстановления после сбоя.
# SSD в RAID10 держат десятки параллельных запросов. Значения по умолчанию
# (1 и 10) рассчитаны на HDD. Больше 200–300 на SATA эффекта не даёт.
```

### Background writer

```ini
bgwriter_delay = 50ms
bgwriter_lru_maxpages = 400
bgwriter_lru_multiplier = 3.0
# Задача — чтобы backend'ы не сбрасывали грязные буферы сами: тогда запись
# попадает прямо в задержку запроса. По умолчанию (200 мс, 100 страниц) это
# всего ~4 МБ/с, при активной записи мало. 50 мс × 400 страниц ≈ 64 МБ/с потолка.
# Почему не агрессивнее: bgwriter может записать страницу, которую тут же снова
# изменят, а это лишний износ SSD. Подстраивается по метрике buffers_backend
# (раздел 10).
```

### Autovacuum: самое важное для filemeta

```ini
autovacuum_max_workers = 6
# По умолчанию 3. В postgres2 каждый бакет — отдельная таблица, плюс таблицы
# Apicurio. Трёх воркеров не хватит, если один застрял на большой таблице.
# Больше 6–8 не нужно: лимит стоимости делится между всеми работающими
# воркерами (см. ниже), и каждый будет работать медленнее.

autovacuum_naptime = 10s
# Как часто проверять каждую базу. По умолчанию 1 мин. При высокой нагрузке
# на запись мёртвые строки накапливаются быстро, поэтому лучше чаще и понемногу.

autovacuum_vacuum_cost_limit = 3000
autovacuum_vacuum_cost_delay = 2ms
# По умолчанию лимит 200 на ВСЕХ воркеров суммарно, это ~8 МБ/с чтения. На SSD
# этого катастрофически мало: VACUUM не успеет за нагрузкой, и таблица
# раздувается. 3000 при задержке 2 мс — это порядка 100–200 МБ/с на всех.
# Почему не -1 (без ограничений): VACUUM может забрать весь I/O и поднять
# задержку коммитов. Если по метрикам VACUUM не успевает, поднимите до 5000.

autovacuum_vacuum_scale_factor = 0.02
autovacuum_analyze_scale_factor = 0.01
# По умолчанию 0.2: на таблице в 500 млн строк VACUUM придёт только после
# 100 млн мёртвых. 2% — это 10 млн, чаще и быстрее за проход. Для filemeta
# ещё ниже, на уровне таблицы (раздел 5).

autovacuum_vacuum_insert_scale_factor = 0.05
# Нагрузка SeaweedFS преимущественно на вставку. Без этого VACUUM на таблице
# только со вставками приходит редко, visibility map не обновляется
# (index-only scan не работает), а заморозка XID откладывается до тяжёлого
# аварийного прохода.

autovacuum_freeze_max_age = 400000000
# По умолчанию 200 млн транзакций. На таблице в сотни гигабайт аварийный
# VACUUM от переполнения XID (anti-wraparound) — это многочасовое полное
# сканирование, которое нельзя прервать. 400 млн делает его вдвое реже.
# До аварийного порога (~2.1 млрд) остаётся большой запас.
# Выше 500–800 млн не ставьте, а возраст XID мониторьте (раздел 10).
```

### Хранение

```ini
default_toast_compression = lz4
# Для больших значений meta (файлы с большим числом чанков) и длинных путей.
# lz4 в разы быстрее pglz при сопоставимом сжатии.
```

### Логи и статистика

```ini
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.max = 10000
pg_stat_statements.track = top
# Статистика по каждому типу запроса. Без неё непонятно, что именно тормозит.
# Накладные расходы около 1–2%.

track_io_timing = on
track_wal_io_timing = on
# Время I/O в pg_stat_statements, pg_stat_io и pg_stat_wal. Без этого нельзя
# доказать, что мы упираемся в диск. Накладные расходы минимальны:
# проверьте, что pg_test_timing показывает < 100 нс.

log_checkpoints = on
log_autovacuum_min_duration = 1s
log_min_duration_statement = 500ms
log_lock_waits = on
log_temp_files = 0
log_line_prefix = '%m [%p] %q%u@%d/%a '
# 500 мс: любой запрос SeaweedFS дольше этого — аномалия. Меньше (50–100 мс)
# при первом же замедлении диска завалит лог миллионами строк и создаст
# дополнительную нагрузку.
# log_temp_files = 0 логирует любой сброс на диск: это сигнал, что work_mem
# мал для какого-то запроса.
```

### Контрольные суммы данных

Задаются при `initdb --data-checksums` или позже через `pg_checksums --enable` на остановленном кластере. На
потребительских SSD без PLP они нужны, чтобы узнать о «тихой» порче данных до того, как она попадёт в бэкапы. Накладные
расходы — единицы процентов CPU.

## 5. Базы, роли, таблицы

```sql
CREATE ROLE seaweed LOGIN PASSWORD '...' CONNECTION LIMIT 250;
CREATE ROLE apicurio LOGIN PASSWORD '...' CONNECTION LIMIT 30;

CREATE
DATABASE seaweedfs OWNER seaweed TEMPLATE template0
  ENCODING 'UTF8' LC_COLLATE 'C' LC_CTYPE 'C';
CREATE
DATABASE apicurio OWNER apicurio;

ALTER
ROLE seaweed SET statement_timeout = '60s';
ALTER
ROLE apicurio SET statement_timeout = '30s';
```

**Collation `C` для базы SeaweedFS.** Сравнение строк идёт побайтово, без ICU и правил языковой сортировки. Это в разы
быстрее для индекса по `(dirhash, name)`. Кроме того, порядок совпадает с побайтовой сортировкой Go, на которую
рассчитана пагинация листингов в SeaweedFS (`name > last ORDER BY name`).

**Лимиты подключений по ролям.** Ни одно приложение не сможет выбрать все `max_connections`. Сумма 250 + 30 + резерв
укладывается в 300.

**`statement_timeout` на уровне ролей.** Зависший запрос не будет держать подключение и горизонт видимости. 60 с для
SeaweedFS — с запасом на листинг огромных директорий.

**Схема таблицы** (задаётся в `createTable` в `filer.toml`):

```sql
CREATE TABLE IF NOT EXISTS "%s"
(
    dirhash
    BIGINT,
    name
    VARCHAR
(
    65535
),
    directory VARCHAR
(
    65535
),
    meta bytea,
    PRIMARY KEY
(
    dirhash,
    name
)
    ) WITH (
          fillfactor = 85,
          autovacuum_vacuum_scale_factor = 0.01,
          autovacuum_analyze_scale_factor = 0.005,
          autovacuum_vacuum_insert_scale_factor = 0.02
          );
```

**`fillfactor = 85`.** В каждой странице остаётся 15% свободного места. Обновление `meta` (изменение файла, его
атрибутов, TTL) не меняет индексированные поля, поэтому запись идёт как HOT-обновление: в ту же страницу, без новой
записи в индексе. Меньше раздувание индекса и меньше записи. Почему не 70: это 30% лишнего места на диске и в кэше, а в
SeaweedFS вставок больше, чем обновлений. Почему не 100 (по умолчанию): почти каждое обновление тогда переносит строку в
другую страницу и добавляет запись в индекс.

**Пороги autovacuum на уровне таблицы.** `filemeta` — самая большая и самая активная таблица, ей нужны пороги в 1%
вместо глобальных 2%.

Для уже существующих таблиц:

```sql
ALTER TABLE filemeta SET (fillfactor = 85, autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_analyze_scale_factor = 0.005, autovacuum_vacuum_insert_scale_factor = 0.02);
-- fillfactor применится только к новым страницам; к существующим — после pg_repack.
```

## 6. SeaweedFS (`filer.toml`)

```toml
[postgres2]
enabled = true
createTable = """ ...схема из раздела 5... """
hostname = "pg-host"
port = 5432
username = "seaweed"
password = "..."
database = "seaweedfs"
schema = ""
sslmode = "disable"            # "require", если сеть не доверенная
connection_max_idle = 50
connection_max_open = 100
connection_max_lifetime_seconds = 300
enableUpsert = true
upsertQuery = """INSERT INTO "%[1]s" (dirhash, name, directory, meta) VALUES ($1, $2, $3, $4)
  ON CONFLICT (dirhash, name) DO UPDATE SET directory = EXCLUDED.directory, meta = EXCLUDED.meta"""
```

**`postgres2`, а не `postgres`.** Он позволяет держать отдельную таблицу на каждый бакет, и удаление бакета превращается
в `DROP TABLE`. В `postgres` удаление бакета — это `DELETE` миллионов строк: гигантский VACUUM и раздувание таблицы.

**`connection_max_open = 100` на один filer.** Это больше оптимума по активным запросам (~40–80) и даёт запас на
всплески. Сумма по всем filer должна быть не больше `CONNECTION LIMIT` роли (250). Значит, до двух filer подключаются
напрямую. Если их больше, ставьте PgBouncer ≥ 1.21 (`pool_mode = transaction`, `max_prepared_statements = 200`,
`default_pool_size = 60`).

**`connection_max_idle = 50`.** Простаивающие соединения не закрываются после каждого всплеска. Новое подключение к
PostgreSQL — это fork процесса и несколько миллисекунд.

**`connection_max_lifetime_seconds = 300`.** Backend PostgreSQL копит кэш каталога. При сотнях таблиц бакетов он может
разрастаться до десятков мегабайт на процесс. Периодическое пересоздание соединений возвращает эту память и выравнивает
нагрузку после переключения на реплику.

**`enableUpsert`.** Один запрос вместо пары «INSERT, ошибка, UPDATE». Без upsert каждая перезапись файла — это неудачная
транзакция с записью в лог ошибок и лишний сетевой обмен.

## 7. Отказоустойчивость и бэкапы

- **Потоковая реплика на отдельном сервере** (асинхронная). На реплике `hot_standby = on` и
  `hot_standby_feedback = off`, если с реплики не читают длинными запросами: `on` переносит раздувание таблиц на мастер.
  Синхронную реплику (`synchronous_standby_names`) не делайте, пока не измерите задержку сети: каждый коммит станет
  ждать ещё и сеть.
- **pgBackRest:** полный бэкап раз в неделю, дифференциальный ежедневно, WAL непрерывно через `archive_command`. Храните
  на другом сервере или в S3, но не в той же SeaweedFS, метаданные которой бэкапите.
- **`fs.meta.save`** в `weed shell` раз в сутки — независимая логическая копия метаданных.
- **Проверка восстановления** раз в месяц: поднять из бэкапа на тестовом стенде и замерить время. Ориентир RTO: 1 ТБ при
  200–400 МБ/с — это 1–1.5 часа плюс replay WAL.
- **ИБП** обязателен. Для дисков без PLP это главная защита от потери данных при пропадании питания.

## 8. Ожидаемая производительность

Это оценки до замеров. Реальные цифры дадут `pg_test_fsync` и `pgbench` (методика в конце раздела).

| Операция                                          | Ориентир                   | Во что упирается     |
|---------------------------------------------------|----------------------------|----------------------|
| Чтение метаданных (lookup), горячие данные        | 50–100+ тыс./с, p99 < 2 мс | CPU, сеть            |
| Запись, `synchronous_commit = on`, 50–100 потоков | 5–15 тыс./с, p99 < 10 мс   | `fsync` дисков       |
| Запись в один поток                               | 300–3000/с                 | 1 коммит = 1 `fsync` |
| Запись с `synchronous_commit = off`               | 20–50 тыс./с               | CPU, объём WAL       |
| То же через контроллер с BBU                      | 20–40 тыс./с при `on`      | CPU                  |
| Листинг директории (страница 1000 записей)        | тысячи в секунду           | размер `meta`        |

- **Объём:** ~0.5–1 КБ на файл вместе с индексом и раздуванием. При комфортном заполнении (≤ 50–60% из 3.5 ТБ) это **~
  1–2 млрд файлов**.
- **Полностью в RAM:** ~150–250 млн файлов. Дальше горячее остаётся в памяти, а холодное читается с SSD с задержкой ~
  0.1–0.5 мс.
- **Восстановление после сбоя:** 2–5 минут (replay до 24 ГБ WAL).
- **Износ дисков:** при 10 тыс. записей в секунду это ~20–40 МБ/с на массив, ~1–1.5 ТБ в сутки на каждый диск. При TBW
  500–1600 ТБ ресурса хватит на **~1–3 года постоянной нагрузки**. При средней нагрузке в 1–2 тыс./с — на много лет.

**Где будет первый предел.** При постоянной записи сначала упрётесь в `fsync`, а именно в рост `wal_sync_time`. Затем,
после исчерпания SLC-кэша, в пропускную способность дисков.

**Методика замера** (запускать не меньше 15 минут, иначе SLC-кэш завысит результаты):

```bash
pg_test_fsync -s 10 -f /pgdata/pg_test
pgbench -n -f write.sql -c 64 -j 16 -T 900 -P 10 seaweedfs
pgbench -n -f write.sql@2 -f read.sql@8 -c 128 -j 16 -T 900 -P 10 seaweedfs
```

Скрипты `write.sql` и `read.sql` — из предыдущего сообщения.

## 9. Риски

**1. Потребительские SSD без PLP. Риск: потеря или порча данных при пропадании питания.** Если прошивка подтверждает
flush, не записав данные, WAL теряет «подтверждённые» коммиты, и в худшем случае страницы данных оказываются испорчены.
Защита: ИБП, проверка `diskchecker.pl`, контрольные суммы данных, реплика, PITR.

**2. Синхронный износ зеркал. Риск: одновременный выход из строя обоих дисков в паре.** В RAID10 оба диска зеркала
получают одинаковую запись. Если они из одной партии, ресурс у них кончится почти одновременно, и массив потеряет данные
во время ребилда.
Защита: мониторинг износа; плановая замена при 70–80% ресурса, по одному диску из пары, со сдвигом по времени; горячий
резерв (hot spare).

**3. Провал производительности.** После исчерпания SLC-кэша и при заполнении диска выше 80% запись на потребительских
SSD падает в разы, и задержки коммитов растут.
Защита: заполнение не выше 70%, неразмеченный запас, регулярный TRIM.

**4. Один сервер — единая точка отказа.** Отказ мастера означает, что вся SeaweedFS недоступна, ведь без метаданных
нельзя прочитать ни один файл.
Защита: реплика плюс процедура переключения (вручную или через Patroni). Время переключения — минуты.

**5. Раздувание `filemeta` и отставание VACUUM.** Таблица и индексы растут, кэш становится менее эффективным, запросы
медленнее.
Защита: настройки autovacuum выше, `idle_in_transaction_session_timeout`, мониторинг мёртвых строк, `pg_repack` по
необходимости.

**6. Переполнение XID (wraparound).** При ~2 млрд транзакций без заморозки PostgreSQL перестаёт принимать запись.
Защита: `autovacuum_vacuum_insert_scale_factor`, мониторинг возраста XID, алерты.

**7. Заполнение диска WAL.** Отказ архивации или застрявший слот репликации держат WAL, пока диск не кончится; тогда
мастер падает.
Защита: `max_slot_wal_keep_size`, алерты на `pg_stat_archiver` и размер `pg_wal`.

**8. Шторм подключений.** Перезапуск нескольких filer одновременно открывает сотни соединений.
Защита: `CONNECTION LIMIT` на ролях, PgBouncer при 3+ filer.

**9. Соседние нагрузки.** Apicurio или прочие процессы съедают I/O и CPU.
Защита: отдельная роль с лимитами, systemd-лимиты на прочие процессы.

**10. Долгое восстановление из бэкапа.** RTO 1–2+ часа при потере и мастера, и реплики.
Защита: реплика как основной путь восстановления, бэкап как последний рубеж; регулярные учения.

**11. Логическое удаление.** Ошибка оператора или клиента массово удаляет файлы в SeaweedFS, и реплика это сразу
повторяет.
Защита: PITR из pgBackRest. Можно добавить отложенную реплику (`recovery_min_apply_delay = 1h`).

## 10. Мониторинг

### Стек

- **Prometheus + Grafana + Alertmanager.**
- **`postgres_exporter`** с дополнительными запросами из этого раздела.
- **`node_exporter`:** CPU, память, диски, `md`-коллектор для mdadm, файловая система.
- **`smartctl_exporter`:** износ и ошибки SSD. Для аппаратного RAID нужен доступ к дискам через контроллер, например
  `smartctl -d megaraid,N`.
- **Метрики filer SeaweedFS** (`-metricsPort`): `SeaweedFS_filerStore_request_seconds` и
  `SeaweedFS_filerStore_request_total` по типам операций. Это задержки глазами приложения.
- **Логи PostgreSQL** в Loki или ELK: медленные запросы, чекпоинты, autovacuum, ожидания блокировок.
- **pgBackRest:** `pgbackrest check` и `pgbackrest info` по cron, с метрикой о последнем успешном бэкапе.

### Алерты

| Что                                               | Warning       | Critical            |
|---------------------------------------------------|---------------|---------------------|
| Свободное место на массиве                        | < 30%         | < 15%               |
| Износ SSD (`Percentage Used` / оставшийся ресурс) | > 60%         | > 80%               |
| SMART: realloc, pending, CRC-ошибки               | рост          | —                   |
| Состояние RAID (degraded, resync)                 | —             | любое               |
| `w_await` дисков                                  | > 5 мс 10 мин | > 20 мс             |
| Утилизация дисков (`%util`)                       | > 80% 15 мин  | —                   |
| Задержка коммита (filer p99, запись)              | > 20 мс       | > 100 мс            |
| Отставание реплики                                | > 30 с / 1 ГБ | > 5 мин / 10 ГБ     |
| Слот репликации неактивен                         | > 5 мин       | > 30 мин            |
| Ошибки архивации (`failed_count` растёт)          | 1 ошибка      | > 10 мин без успеха |
| Последний успешный бэкап                          | > 26 ч        | > 50 ч              |
| Возраст XID базы                                  | > 600 млн     | > 1 млрд            |
| Самая длинная транзакция / idle in transaction    | > 5 мин       | > 30 мин            |
| Подключения от `max_connections`                  | > 70%         | > 90%               |
| Cache hit ratio                                   | < 99%         | < 95%               |
| Чекпоинты по объёму WAL (`checkpoints_req`)       | > 10% от всех | —                   |
| Мёртвые строки в `filemeta`                       | > 10%         | > 20%               |
| Deadlocks / откаты (rollback)                     | рост          | —                   |
| PostgreSQL недоступен                             | —             | 1 мин               |

### Дашборды

- **Обзор:** операции filer в секунду (TPS), p50/p99 задержки filer, подключения по состояниям, cache hit, отставание
  реплики.
- **Диски:** IOPS, МБ/с, `w_await`, `%util` по каждому диску (видно, если один диск в RAID «тормозит»), заполнение,
  износ, температура.
- **WAL и чекпоинты:** WAL в МБ/с, `wal_sync_time / wal_sync` (средняя задержка `fsync` — ключевая метрика),
  длительность чекпоинтов, `buffers_backend` против `buffers_clean`.
- **Vacuum:** мёртвые строки по таблицам, время последнего autovacuum, активные воркеры, возраст XID.
- **Запросы:** топ по `pg_stat_statements` (total time, mean, calls).

### Ключевые SQL-запросы для экспортера и ручной диагностики

Средняя задержка `fsync` WAL — главный индикатор того, упираемся ли в диски (норма для этих SSD — 0.3–2 мс):

```sql
SELECT wal_sync,
       round((wal_sync_time / NULLIF(wal_sync, 0)):: numeric, 3) AS avg_sync_ms,
       pg_size_pretty(wal_bytes)                                 AS wal_total
FROM pg_stat_wal;
```

Чекпоинты и bgwriter (в PG16 это `pg_stat_bgwriter`):

```sql
SELECT checkpoints_timed,
       checkpoints_req,
       buffers_checkpoint,
       buffers_clean,
       buffers_backend,
       maxwritten_clean
FROM pg_stat_bgwriter;
```

Если `checkpoints_req` растёт, увеличьте `max_wal_size`. Если `buffers_backend` велик относительно `buffers_clean`,
усильте bgwriter. Если растёт `maxwritten_clean`, увеличьте `bgwriter_lru_maxpages`.

Раздувание и VACUUM:

```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       n_tup_hot_upd * 100 / NULLIF(n_tup_upd, 0)                        AS hot_upd_pct,
       last_autovacuum,
       last_autoanalyze,
       pg_size_pretty(pg_total_relation_size(relid)) AS size
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;
```

`hot_upd_pct` должен быть 80%+. Если меньше, `fillfactor` не помогает: проверьте его и сделайте `pg_repack`.

Возраст XID:

```sql
SELECT datname, age(datfrozenxid)
FROM pg_database
ORDER BY 2 DESC;
SELECT relname, age(relfrozenxid)
FROM pg_class
WHERE relkind = 'r'
ORDER BY 2 DESC LIMIT 10;
```

Долгие транзакции, которые держат горизонт видимости:

```sql
SELECT pid, usename, state, now() - xact_start AS xact_age, left (query, 80)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start LIMIT 10;
```

Плюс проверьте `pg_replication_slots` (`xmin`, `active`) и `pg_prepared_xacts`: брошенный слот или подготовленная
транзакция тоже держат горизонт.

Репликация и архив:

```sql
SELECT application_name,
       state,
       replay_lag,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag_bytes
FROM pg_stat_replication;

SELECT slot_name,
       active,
       wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

SELECT archived_count, failed_count, last_archived_time, last_failed_time
FROM pg_stat_archiver;
```

Cache hit и I/O по типам backend'ов (в PG16 есть `pg_stat_io`):

```sql
SELECT datname, round(100.0 * blks_hit / NULLIF(blks_hit + blks_read, 0), 2) AS hit_pct
FROM pg_stat_database
WHERE datname IN ('seaweedfs', 'apicurio');

SELECT backend_type, object, context, reads, writes, fsyncs
FROM pg_stat_io
WHERE writes > 0
   OR fsyncs > 0
ORDER BY writes DESC;
```

Если в `pg_stat_io` много `writes` у `client backend`, backend'ы сами сбрасывают страницы: усильте bgwriter или
проверьте чекпоинты.

Топ запросов:

```sql
SELECT calls,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       round(total_exec_time::numeric)   AS total_ms,
       round(blk_write_time::numeric)    AS write_ms, left (query, 100)
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 15;
```

Износ SSD (по cron или через `smartctl_exporter`):

```bash
smartctl -A /dev/sdX | egrep -i 'wear|percent|lbas_written|realloc|pending|crc|temperature'
```

## 11. Порядок внедрения

1. Собрать массив, отключить кэш дисков или включить write-back на контроллере с BBU, выставить заполнение и
   over-provisioning.
2. Прогнать `fio` (15+ мин) и `pg_test_fsync`, записать базовые цифры.
3. Применить настройки ОС, huge pages, systemd-лимиты.
4. `initdb --data-checksums`, конфиг из раздела 4, базы и роли из раздела 5.
5. Нагрузочный тест `pgbench` 15+ минут: проверить, что `avg_sync_ms` и p99 в норме, а чекпоинты идут по времени.
6. Настроить pgBackRest и реплику, проверить восстановление.
7. Поднять мониторинг и алерты **до** запуска SeaweedFS.
8. Подключить filer, неделю наблюдать за autovacuum, долей HOT-обновлений, `wal_sync_time` и износом. После этого
   корректировать `max_wal_size`, `autovacuum_vacuum_cost_limit`, bgwriter и при необходимости `commit_delay` или
   `synchronous_commit`.

Если пришлёте результаты шагов 2 и 5, можно скорректировать значения под реальные диски.
